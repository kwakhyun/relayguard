# RelayGuard 조사 노트

조사 기준일: **2026-10-23, 한국 시간**. 인터넷 검색 후 아래 원문을 직접 열어 확인했다. 사건 발생일, 탐지일, 문서 발표일은 서로 다를 수 있어 구분했다. 수치는 공개 당시 공급자의 설명이며, 독립적으로 피해 규모를 검증한 결과가 아니다.

## 조사에서 선택한 문제

RelayGuard는 **연동용 API 토큰이 유출되었을 때 허용된 기능과 데이터 반출량을 제한하는 자체 호스팅 게이트웨이**다. 모든 해킹을 예방하는 제품은 아니다. 이번 조사에서는 상용 서비스의 연동 자격 증명 탈취와 그 이후의 데이터 접근을 구현 가능한 범위로 선택했다.

상용 SaaS의 정상 API와 유효한 토큰만으로도 데이터가 유출될 수 있다. 따라서 요청이 로그인에 성공했는지만 확인하는 것으로는 충분하지 않다. 연동별로 접근 가능한 경로와 메서드를 좁히고, 만료와 해지를 적용하고, 호출량과 응답량을 제한해야 한다는 것이 이 프로젝트의 설계 판단이다. 아래 사건에 이 게이트웨이를 설치했다면 피해가 반드시 없었을 것이라는 주장은 하지 않는다.

OWASP는 기능별 권한 검사를 일관되게 적용하고, API 호출의 자원 사용량에 한계를 두도록 설명한다. 여기서는 이를 경로/메서드 정책과 호출 및 응답량 제한으로 구체화했다. [OWASP API5](https://api-security.owasp.org/editions/2023/en/0xa5-broken-function-level-authorization/), [OWASP API4](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/)

OAuth 구현 자체를 확장한다면 토큰 재사용 방지, 권한 제한, refresh token 회전 등은 [IETF RFC 9700, 2025년 1월](https://datatracker.ietf.org/doc/html/rfc9700)의 권고를 따라야 한다. 현재 제품의 제한된 bearer token은 완전한 OAuth 서버나 OAuth 프로토콜 적합성 구현을 의미하지 않는다.

## 무엇을 줄일 수 있고, 무엇을 해결하지 못하는가

### 보호가 성립하는 배치

```text
연동 앱 / 배치 작업
    │ 제한된 RelayGuard 토큰
    ▼
RelayGuard: 인증 → 정책 검사 → 호출/응답량 제한 → 감사 기록
    │ 서비스 전용 자격 증명
    ▼
사내 API / SaaS API
```

연동 앱이 RelayGuard를 호출할 수 있어야 한다. SaaS가 고정된 직접 OAuth 연동만 제공한다면 이 게이트웨이를 그대로 끼울 수 없다. 실제 제공자에 접근하는 자격 증명은 최소 권한으로 발급하고, 가능하다면 제공자 측에서도 게이트웨이의 네트워크 또는 워크로드만 허용해야 한다.

이 조건에서 **RelayGuard 토큰만 탈취한 공격자**는 지정되지 않은 기능을 호출할 수 없고, 설정한 호출 수와 반출량을 초과할 수 없다. 해지는 이후 요청을 중단한다. 감사 기록은 어느 토큰이 어떤 작업을 시도했는지 조사할 근거가 된다.

### 해결하지 못하는 문제

- **서비스 원본 토큰 탈취와 우회:** 공격자가 실제 SaaS 토큰을 이미 가지고 직접 API를 호출하면 게이트웨이 정책은 적용되지 않는다. RelayGuard 토큰 해지도 제공자 토큰의 해지를 뜻하지 않는다.
- **정상 권한 안에서의 유출:** 허용된 조회 결과는 한도 이내에서 유출될 수 있다. 응답 바이트는 데이터의 민감도를 판별하지 않는다. 여러 유효 토큰을 합친 유출량도 별도 조직 단위 통제가 없으면 커질 수 있다.
- **객체별 권한과 쿼리의 의미:** 경로가 같아도 다른 고객의 데이터나 더 민감한 필드를 조회할 수 있다. SQL/SOQL, GraphQL, 검색 쿼리를 해석하는 권한 엔진은 아니며, 객체별 권한 검사는 서비스가 수행해야 한다.
- **이미 진행 중인 작업:** 해지는 완료된 유출을 되돌리지 못한다. 서비스가 이미 수신한 쓰기 작업의 효과를 취소하지 못하며, 현재 진행 중인 요청의 중단 보장은 별도의 동시성 설계가 필요하다.
- **게이트웨이/호스트/관리자 침해:** 공격자가 프로세스 메모리나 운영 비밀, 관리자 권한을 얻으면 이 신뢰 경계가 무너질 수 있다. 운영 비밀의 보관, TLS, 관리자 인증과 네트워크 격리는 배포 책임이다.
- **피싱, DNS와 SDK 공급망, 랜섬웨어, 원격 코드 실행, 인터넷 규모 DDoS:** 별도의 예방 및 탐지 체계가 필요하다. 이 프로젝트는 WAF, EDR, DLP 또는 전체 보안 관제 제품을 대체하지 않는다.

공급망은 이 프로젝트 자체에도 적용된다. [Trivy의 2026-03-21 공식 보안 권고](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23)는 3월 19일 변조된 릴리스/Action 태그와 3월 22일 Docker 이미지 배포를 설명한다. 따라서 오픈소스 보안 도구를 사용한다는 사실만으로 안전을 가정하지 않고, 의존성과 CI 권한을 작게 유지하며 배포 산출물의 출처를 관리해야 한다.

## 로컬 시연의 성공 기준

실제 회사나 고객 데이터 대신 합성 CRM 데이터를 사용한다. 같은 토큰으로 정상 조회 성공, 허용되지 않은 내보내기/메서드 거부, 과도한 호출 거부, 큰 응답 및 누적 반출량 초과 거부, 해지 이후 재사용 실패를 확인한다. 관리자 화면과 감사 기록에서 결과가 일치해야 하며, 각 거부가 실제 서비스 호출 전인지 응답 전달 전인지 구분한다.

이 시연은 공개 사고의 공통 위험을 재현하는 방어 실험이다. 실제 서비스에 대한 침투 테스트나 해당 사고의 공격 코드를 재현한 것이 아니다.
