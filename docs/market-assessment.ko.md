# RelayGuard 공개 가치 평가

조사 기준: 2026년 10월 30일. 공식 제품 문서와 공개 저장소, 현재 소스의 기능 범위를 비교했다. 이는 고객 인터뷰나 외부 보안 감사 결과가 아니다.

**작은 오픈소스 도구로 공개하고 피드백을 받을 가치는 있다. 범용 보안 플랫폼으로 경쟁하거나 유료 수요가 검증됐다고 말할 근거는 없다.** 가장 설득력 있는 용도는 하나의 Bearer API를 사용하는 내부 자동화나 외부 협력자에게 원본 토큰 대신 짧은 수명과 데이터 한도를 가진 키를 제공하는 것이다.

## 확인된 사실과 해석

이번 개선을 게시하기 전 조사 시점의 [공개 저장소](https://github.com/kwakhyun/relayguard)는 별 0개, 포크 0개, 공개 이슈 0개, 커밋 3개였다. 이는 공개 관심과 기여가 아직 형성되지 않았다는 신호다. 설치 수, 실제 사용자 수, 운영 사용 여부는 이 수치로 알 수 없다. 저장소 공개와 Docker 다운로드 가능 여부도 제품 수요의 증거는 아니다.

현재 확인 가능한 가치는 MIT 소스, 직접 실행하는 합성 데이터 데모, 명시적인 정책과 실패 동작, 재현 가능한 테스트에 있다. 독립 보안 감사, 외부 운영 사례, 지원 체계와 장기 유지보수 실적은 확인되지 않았다. 기업가치나 매출 잠재력을 금액으로 환산할 근거도 없다.

## 기존 도구와 비교

| 대안 | 이미 제공하는 관련 기능 | RelayGuard를 선택할 이유와 불리한 점 |
| --- | --- | --- |
| Kong | 응답의 사용자 정의 헤더를 비용 단위로 계산하는 제한, 로컬/DB/Redis 카운터. [공식 문서](https://developer.konghq.com/plugins/response-ratelimiting/) | RelayGuard는 실제 응답 바이트를 직접 세고 전체 응답을 보류한 뒤 승인한다. 이 조합을 작은 배포로 제공하는 것이 장점이다. Kong으로 같은 통제를 구현할 수 없다는 뜻은 아니다. 이미 Kong을 운영한다면 플러그인 확장이 추가 프록시보다 나을 수 있다. |
| Apache APISIX | 요청 횟수 제한, 고정/슬라이딩 창, Redis 계열 공유 카운터. [공식 문서](https://apisix.apache.org/docs/apisix/plugins/limit-count/) | RelayGuard의 바이트 한도는 요청 횟수 제한과 측정 대상이 다르다. 반면 분산 운영과 다양한 게이트웨이 기능이 필요하면 APISIX가 더 적합한 출발점이다. |
| Ory Oathkeeper | 경로와 메서드 규칙, 들어온 자격 증명을 백엔드가 이해하는 헤더 등으로 바꾸는 처리. [공식 문서](https://www.ory.com/docs/oathkeeper/pipeline/mutator) | 프록시에서 자격 증명을 분리하는 아이디어 자체는 새롭지 않다. RelayGuard는 한 서비스 계정에 대한 키 발급과 바이트 한도라는 좁은 흐름에 집중한다. |
| OpenBao | 동적 비밀과 서비스 토큰의 lease, 갱신과 폐기. 임의 KV 비밀에는 동일한 lease 보장이 적용되지 않는다. [공식 문서](https://openbao.org/docs/concepts/lease/) | 실제 제공자 자격 증명 발급과 회전이 목적이라면 비밀 관리 시스템을 우선 검토해야 한다. RelayGuard는 원본 토큰을 회전하거나 KMS를 대체하지 않는다. |
| LiteLLM | 가상 키, 모델 접근, 비용 예산, RPM/TPM 제한. 해당 키 관리 구성은 PostgreSQL을 사용한다. [공식 문서](https://docs.litellm.ai/docs/proxy/virtual_keys) | LLM 비용과 모델 사용 통제가 목적이라면 LiteLLM이 더 직접적이다. RelayGuard의 일반 HTTP 응답 바이트는 토큰 수나 청구 금액이 아니다. |
| Nango | 제공자 자격 증명을 서버에 보관하고 프록시에 주입하는 연동 흐름. [공식 예제](https://nango.dev/blog/how-to-build-ai-agent-integrations-using-the-nango-management-mcp) | 다수 SaaS 연동과 OAuth 흐름이 필요하면 이 범주의 플랫폼이 더 적합하다. 현재 자체 호스팅 문서는 Enterprise 경로를 안내한다. [배포 문서](https://nango.dev/docs/guides/platform/self-hosting/self-hosting) 저장소 라이선스는 ELv2이므로 MIT 오픈소스와 동일한 조건으로 묶지 않았다. [라이선스](https://github.com/NangoHQ/nango/blob/master/LICENSE) |

비교는 명시된 기능과 현재 문서에 한정한다. 경쟁 제품의 모든 확장 기능을 조사한 결과나 성능 비교가 아니며, 기능 수를 시장점유율로 해석하지 않는다.

## 도입이 맞는 경우

- 클라이언트의 요청 URL과 Authorization 헤더를 바꿀 수 있다.
- 하나의 HTTPS origin과 Bearer 서비스 계정으로 충분하다.
- 반환 데이터가 작은 JSON 또는 텍스트이며, 전체 응답을 기다릴 수 있다.
- 짧은 작업에 필요한 경로만 허용하고 키별 총 요청 수와 총 바이트를 정하고 싶다.
- 운영자가 로컬 SQLite 상태와 백업을 관리할 수 있다.

예를 들어 외부 협력자의 하루짜리 조회 작업에 GET 경로만 열고, 허용되는 전체 조회량을 정하는 경우다. 이미 받은 데이터의 사용은 통제하지 못한다. 클라이언트가 원본 토큰을 계속 가지고 있다면 RelayGuard를 우회할 수 있다.

여러 고객 계정의 OAuth 갱신, 객체별 권한, 대용량 파일과 스트리밍, SSO/RBAC, 다중 리전이나 고가용성이 필수인 경우에는 현재 범위가 맞지 않는다. 인터넷에 노출된 모든 API의 보안 문제를 해결한다는 홍보도 부적절하다.

## 이번 개선의 판단 근거

아래 항목은 v0.2.0 공개 프리뷰를 위해 소스에 반영한 개선 사항이다. 공개 이미지 `0.1.1`의 기능으로 소급해서 설명하지 않는다. 배포 여부와 검증 기록은 [변경 기록](../CHANGELOG.md), [검증 보고서](verification.md)에서 확인한다.

| 도입을 막던 문제 | 소스에서 보완한 내용 | 남는 한계 |
| --- | --- | --- |
| 분당 제한 이하로 계속 가져가면 키 수명 전체의 반출량을 정할 수 없음 | 재시작과 분 경계 이후에도 유지되는 키별 총 요청 수와 총 응답 바이트 한도 | 기존 키에 총 한도가 자동으로 생기지 않는다. 여러 키의 조직 합산 예산은 없다. |
| 운영 연결 전에 정책의 허용 범위를 확인하기 어려움 | 실제 경로/쿼리/IP 검사 함수를 사용하는 오프라인 정책 검사와 기대 결과 사례 파일 | 인증, 실시간 사용량, 헤더/본문, 제공자 응답은 별도로 검증해야 한다. |
| 프로세스가 살아 있어도 저장소 쓰기가 막힐 수 있음 | 로컬 저장소 쓰기 준비를 확인하는 `/readyz`, 설정 검사, 파일 기반 비밀 주입 | 준비 상태가 감사 체인 전체의 무결성이나 upstream 정상 동작을 보증하지 않는다. |
| 동기 SQLite 작업이 비동기 요청 처리를 지연시킬 수 있음 | DB 작업을 작업 스레드로 옮기고 잠금 대기와 취소 경로를 검증 | SQLite 쓰기 직렬화와 디스크 처리량 한계는 남는다. 확장성 수치를 약속하지 않는다. |
| 기능과 문서만으로 콘솔의 실제 상태 전환을 신뢰하기 어려움 | 작업별 콘솔, 한 번만 표시하는 키 흐름, 비동기 응답 회귀 테스트와 설치한 wheel 검사 | 자동 DOM 테스트는 화면 배치나 모든 보조공학 사용성을 증명하지 않는다. |
| 한국어 중심 설명과 넓은 보안 메시지가 도입 대상을 흐림 | 영어 시작 안내, 비교 자료, 프로토콜 제한과 채택 기준 공개 | 영어 콘솔, 외부 사용 사례, 커뮤니티 기여는 별도 과제다. |

## 공개와 홍보의 범위

지금 적절한 메시지는 “작은 HTTP 연동을 위한 제한된 자격 증명 프록시를 공개하며 사용성과 정책 경계에 대한 피드백을 구한다”이다. 독립 검토 없이 “검증된 보안”, “데이터 유출 방지 보장”, “엔터프라이즈 준비 완료” 같은 표현은 쓰지 않는다.

첫 공개의 목적은 다운로드 숫자보다 **맞는 사용자가 실제 연동을 끝낼 수 있는지 확인하는 것**이다. 다음은 달성했다고 주장하는 성과가 아니라, 추가 개발을 결정하기 위한 제안 기준이다.

1. 서로 다른 외부 사용자 3명이 안내만 보고 로컬 데모와 자기 API의 읽기 경로를 연결한다. 막힌 단계와 필요한 프로토콜을 기록한다.
2. 그중 최소 1명이 실제 비민감 작업에 한도와 폐기를 사용하고, 기존 방식보다 운영 부담이 줄었는지 설명한다.
3. 보안 경계에 대한 독립 코드 검토를 받고 결과와 수정 내용을 공개한다. 취약점의 세부 내용은 먼저 [보안 제보 절차](../SECURITY.md)로 처리한다.
4. 실제 사용 패턴이 확인되면 그 부하에서 지연, DB 증가량, 복구 시간을 재현 가능하게 측정한다.

사용자가 반복해서 요구하기 전에는 OAuth 제공자 목록, KMS, 조직 관리, 분산 DB를 한꺼번에 추가하지 않는다. 초기 도구의 좁은 장점을 흐리고 운영할 코드를 늘릴 수 있기 때문이다. 공개 가치는 충분하지만, 시장 수요와 운영 신뢰는 공개 이후 증거로 쌓아야 한다.
